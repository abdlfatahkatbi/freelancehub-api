# شرح آخر تعديل في المشروع

## ما هو آخر شيء تم عمله؟

تمت إضافة اختبار شامل للـ API باستخدام:

- **اختبار نهاية إلى نهاية (End-to-End Test)**: يشغل التطبيق كما يعمل فعليًا.
- **Supertest**: يرسل طلبات HTTP حقيقية إلى مسارات NestJS.
- **قاعدة بيانات اختبار (Test Database)**: قاعدة PostgreSQL منفصلة عن قاعدة التطوير.

الهدف من الاختبار هو تنفيذ سيناريو القسم الثامن من ملف المتطلبات:

```text
Sara = عميلة
Ahmed = مستقل
Layla = مستقلة
Admin = مدير
```

الاختبار موجود في:

```text
test/acceptance.e2e-spec.ts
```

## لماذا أضفنا هذا الاختبار؟

بدل أن نجرب كل شيء يدويًا من Swagger أو Postman، الاختبار ينفذ السيناريو كاملًا بشكل آلي.

إذا تغير الكود مستقبلًا وحدث خطأ في:

- الرصيد.
- قبول العرض.
- العقد.
- التسليم.
- العمولة.
- الصلاحيات.

فإن الاختبار سيفشل ويخبرنا أن هناك سلوكًا لم يعد يعمل كما هو مطلوب.

## ماذا يفعل الاختبار بالترتيب؟

### 1. تجهيز قاعدة البيانات

في بداية الاختبار يتم التأكد من وجود متغير البيئة:

```text
TEST_DATABASE_URL
```

هذا المتغير يجب أن يشير إلى قاعدة PostgreSQL مخصصة للاختبارات.

السبب مهم جدًا: لا نريد أن يحذف الاختبار بيانات قاعدة التطوير أو بيانات المشروع الحقيقية.

قبل بدء السيناريو، يتم حذف البيانات القديمة من قاعدة الاختبار فقط.

بعد انتهاء الاختبار، يتم تنظيف البيانات مرة أخرى وإغلاق التطبيق.

### 2. إنشاء المستخدمين

يتم إنشاء المستخدمين التاليين من خلال مسار التسجيل:

```text
Sara  -> CLIENT
Ahmed -> FREELANCER
Layla -> FREELANCER
Bob   -> CLIENT
```

ويتم إنشاء مستخدم Admin مباشرة داخل قاعدة الاختبار، لأنه لا يمكن تسجيل Admin من مسار التسجيل العادي.

بعد التسجيل، يحصل كل مستخدم على:

- رمز دخول JWT.
- محفظة.
- ملف FreelancerProfile إذا كان دوره FREELANCER.

### 3. إيداع Sara مبلغ 300

يرسل الاختبار:

```http
POST /wallet/deposit
```

بالمبلغ:

```json
{
  "amount": "300.00"
}
```

ثم يتأكد أن رصيد Sara أصبح:

```text
300
```

كما يتأكد أن عملية الإيداع تسجلت في دفتر العمليات (Ledger).

### 4. إنشاء مشروع

تنشئ Sara مشروعًا بعنوان:

```text
logo design
```

ويكون المشروع في البداية بالحالة:

```text
OPEN
```

### 5. إرسال العروض

يرسل Ahmed عرضًا بقيمة:

```text
200
```

وترسل Layla عرضًا آخر.

بعد ذلك يحاول Ahmed إرسال عرض ثانٍ على نفس المشروع.

الاختبار يتأكد أن النتيجة هي:

```http
409 Conflict
```

والسبب أن قاعدة البيانات تمنع أكثر من عرض واحد من نفس المستقل على نفس المشروع.

### 6. قبول عرض Ahmed

ترسل Sara:

```http
POST /proposals/:id/accept
```

الاختبار يتأكد من النتائج التالية:

```text
رصيد Sara       = 100
قيمة العقد       = 200
حالة العقد       = HELD
حالة المشروع     = IN_PROGRESS
حالة عرض Ahmed   = ACCEPTED
حالة عرض Layla   = REJECTED
```

عملية القبول كلها موجودة داخل Transaction واحدة.

إذا فشلت أي خطوة، يتم التراجع عن كل الخطوات السابقة.

### 7. اختبار الرصيد غير الكافي

ينشئ الاختبار مشروعًا ثانيًا ويحاول Sara قبول عرض قيمته `200` بينما رصيدها `100` فقط.

المطلوب أن يرجع السيرفر:

```http
400 Bad Request
```

والأهم أن الاختبار يتأكد من عدم حدوث أي تغيير:

- رصيد Sara يبقى `100`.
- المشروع يبقى `OPEN`.
- العرض يبقى `PENDING`.
- لا يتم إنشاء عقد.

### 8. رفع التسليم

يرسل Ahmed ملف PDF إلى:

```http
POST /projects/:projectId/delivery
```

الاختبار يستخدم ملف PDF تجريبيًا داخل الذاكرة، ولا يحتاج إلى ملف حقيقي موجود على الجهاز.

ثم يتأكد أن:

- Ahmed يستطيع تنزيل التسليم.
- Sara تستطيع تنزيل التسليم.

### 9. موافقة Sara على التسليم

ترسل Sara:

```http
POST /projects/:projectId/delivery/approve
```

بعد الموافقة يتم التحقق من:

```text
قيمة العقد             = 200
حصة Ahmed              = 180
عمولة المنصة           = 20
رصيد Ahmed             = 180
رصيد Admin             = 20
حالة العقد             = RELEASED
حالة المشروع           = COMPLETED
```

ويتم التأكد أيضًا من إنشاء سجلين ماليين:

```text
PAYOUT
COMMISSION
```

### 10. منع الدفع مرتين

يحاول الاختبار تنفيذ موافقة ثانية على نفس التسليم.

النتيجة المطلوبة:

```http
409 Conflict
```

كما يتأكد أن رصيد Ahmed لم يتغير وبقي:

```text
180
```

وهذا يحمي النظام من الضغط على زر الموافقة مرتين أو من تكرار نفس الطلب.

### 11. اختبار الصلاحيات والملكية

يحاول Ahmed تعديل عرض Layla.

النتيجة المطلوبة:

```http
403 Forbidden
```

ثم تحاول Sara تعديل مشروع يخص Bob.

والنتيجة المطلوبة أيضًا:

```http
403 Forbidden
```

هذا يختبر حماية الملكية (Ownership Protection) ومنع الوصول إلى بيانات مستخدم آخر.

### 12. اختبار الحظر

يقوم Admin بحظر Ahmed.

بعد ذلك يستخدم Ahmed نفس التوكن القديم لمحاولة الوصول إلى API.

النتيجة المطلوبة:

```http
401 Unauthorized
```

السبب أن النظام يعيد تحميل المستخدم من قاعدة البيانات مع كل طلب، لذلك يصبح الحظر فعالًا حتى على التوكن القديم.

### 13. اختبار تحديد محاولات تسجيل الدخول

يرسل الاختبار خمس محاولات تسجيل دخول خاطئة.

كل محاولة من الخمس ترجع:

```http
401 Unauthorized
```

المحاولة السادسة خلال نفس الدقيقة يجب أن ترجع:

```http
429 Too Many Requests
```

وهذا يختبر حماية تسجيل الدخول من المحاولات الكثيرة.

## الملفات التي تغيرت

تمت إضافة:

```text
test/acceptance.e2e-spec.ts
```

وتم تحديث:

```text
test/app.e2e-spec.ts
```

السبب في تحديث الاختبار القديم أن المسار `/` محمي حاليًا بالحارس العام (Global JWT Guard)، لذلك أصبح المتوقع منه:

```http
401 Unauthorized
```

بدل `200 OK`.

## كيف أشغل الاختبار؟

### الخطوة الأولى: إنشاء قاعدة اختبار

يجب أن تكون لديك قاعدة PostgreSQL منفصلة، مثل:

```text
freelancehub_test
```

### الخطوة الثانية: تحديد رابط قاعدة الاختبار

في PowerShell:

```powershell
$env:TEST_DATABASE_URL="postgresql://USER:PASSWORD@localhost:5432/freelancehub_test"
```

استبدل:

- `USER` باسم مستخدم PostgreSQL.
- `PASSWORD` بكلمة المرور.
- `localhost` بعنوان PostgreSQL إذا كان مختلفًا.
- `freelancehub_test` باسم قاعدة الاختبار.

### الخطوة الثالثة: تجهيز الجداول

```powershell
$env:DATABASE_URL=$env:TEST_DATABASE_URL
npx prisma db push
```

هذا ينشئ الجداول في قاعدة الاختبار.

### الخطوة الرابعة: تشغيل الاختبار

```powershell
npm run test:e2e -- --runInBand
```

### تشغيل اختبار السيناريو وحده

```powershell
npx jest --config ./test/jest-e2e.json --runInBand test/acceptance.e2e-spec.ts
```

## ملاحظة مهمة

إذا لم يكن `TEST_DATABASE_URL` مضبوطًا، فالاختبار يتوقف عمدًا ولا يبدأ.

هذا تصرف أمني مقصود حتى لا يتم تشغيل الاختبار بالخطأ على قاعدة التطوير وحذف بياناتها.

آخر تحقق تم عمله:

- البناء (Build) نجح.
- الفحص (Lint) نجح.
- اختبار `app.e2e-spec.ts` نجح.
- اختبار السيناريو الكامل يحتاج فقط إلى ضبط `TEST_DATABASE_URL` وتشغيله على PostgreSQL اختبارية.
